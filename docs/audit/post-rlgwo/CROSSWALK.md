## Disposition vocabulary and rules

| Disposition | Meaning here |
|---|---|
| resolved and independently verified | the original concern is removed in code, shown by before/after source or test evidence, and an independent review, mutation controls and native evidence are recorded for the scope stated |
| implemented but not fully verified | the current implementation is coherent with the original concern, but verification is partial (unit only, native on earlier bytes, or not re-proved by this audit) |
| partly resolved | some of the original concern was addressed; a named residual remains |
| still implicit or vulnerable | unchanged, or changed without addressing the original concern; or a defect demonstrated now |
| superseded by a different implementation | the machine no longer exists in that form |
| no longer applicable | the machine still exists but no longer acts (for example, a workflow locked to one past PR) |
| unable to determine | evidence insufficient for any of the above |

Rules applied where a lane gave no specific disposition: a machine untouched since `f71fef6c`
whose original implementation class was implicit is **still implicit or vulnerable**; one whose
original class was partly explicit or explicit, with no open defect, is **implemented but not
fully verified** (the audit inspected but did not re-prove it). Integrator corrections to lane
dispositions are listed in [REPORT.md](REPORT.md#integrator-verification-corrections-and-downgrades).
