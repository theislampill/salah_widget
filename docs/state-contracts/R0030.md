## 2. Machine CFG-SETTINGS-RESET (`src/native/index.html`, settings block)

Owner: the settings block. New state: `_setReset` (the Reset-scoped owner, distinct from the panel lookup token
`{session,edit,seq}`), `_setResetFailed` (the next open reports a closed-panel detection failure),
`_setApplyFault` (G3 report). `_SET_PREF_IDS` gains `label` so a display-name edit is versioned like the other
post-dispatch field edits (G2-i).

`_setReset = {prefOwner, session, phase, save, release}`; `phase ∈ detecting | held | applying | applied | failed`.

| From | Event | Guard | To / effect |
|---|---|---|---|

Invariants (issue §5.1 I1–I6). I1: after a successful clear the pre-dispatch location is re-persisted only after a
newer explicit location intent, or in the G1b-a case (dispatching panel open, detection failed, the form visibly
shows that site, the user close-saves). I2: close/reopen and display-name edits are not location intents. I3: post-
dispatch field edits survive every phase, close and reopen. I4: nothing claims the cleared record (pin name/ARIA,
`_setLocationSaved`, `CONFIG.source` read by `qaState().config.configSource`) until a later successful save. I5:
runtime and persistence outcomes stay separate (R0011). I6: settings apply rejections are observed (§3).

Classifier neutrality: the marker change keeps `origin||source` equal, and `savedAt` is persistence metadata, so
`classifyConfigChange(old, new)` is `none` (ES30-06 asserts it). `applyConfig` and `config.js` are unchanged; the
three `applyConfig(` occurrences (definition, settings commit, Reset) are kept.

## 3. Commit-failure contract (PRA-F-33, G3-a)

`_commitSettings` and the deferred Reset commits go through `_applySettings(cfg,save)`, which attaches
`.then(success, failure)`; `_resetLocal` awaits its apply inside `try/catch`. A rejection is logged once
(`console.error`) and sets `_setApplyFault` (sanitised error name); `_outcomeMessage()` then appends
"Settings could not be applied (<name>). Reload the widget to try again." to the existing persistence line in the
live region and the panel status (`err` class). The published persistence fact is kept (no rollback, no retry, no
second loop); a later settled apply withdraws the line. In every non-failure path `_setApplyFault` is null and the
text is byte-identical to main.

## 5. Decision gates

- **G1 = A** (owner): Reset authority survives close/reopen; close commits only post-dispatch edits merged into the
  target when it lands. Implemented with one addition the issue did not spell out: a target that lands while a
  *later* session is open is held until that session closes, so that session's form and runtime never diverge and
  `r000f-intent` close/reopen (coarse) stays byte-unchanged.
- **G1a = A1**, **G1b = (a)**, **G2 = (i)**, **G5 = (a)** (owner): as §2.
- **G3 = (a)** (owner): the failure line above. **Wording PENDING-OWNER** (the issue says "wording approved by the
  owner"; the decision records the option, not the sentence). Smallest alternatives: keep; or the shorter
  "Settings could not be applied."
- **G4 = retain** (owner): `units`/`lp`/`seed` stay broad (R0003 D3/D4). Two `seed` authorities remain: renderers
  read the fragment (`q.get("seed")`), settings carry `CONFIG.seed`. No performance claim. Reconsideration trigger
  (recorded): a measured avoidable-request or scene-rebuild cost of a `units`-only change that the owner deems
  material, or a reported case where a saved `seed` differs from the embed's `seed` and the visible field does not
  follow the saved one.
- **G5 status line (new copy, PENDING-OWNER wording):** the resolver-site path cannot say "Detecting your area…" or
  "Using estimated area" truthfully; it shows "Using configured site: <label>". Alternatives: keep; or no hint.

## 8. Deviations and limits

- **D1 (GPS/search).** The issue's table lists "search candidate shown" and "GPS success" as the superseding
  events. The candidate ends Reset at the **request** (place-search start, GPS pin click), as main already did,
  because `_usePrecise` is reserved for R0031's slice and a pending search must not be silently dropped by a Reset
  that lands first. Consequence: a failed GPS/search request after Reset leaves the visible form (old site) as the
  location authority, like G1b-a. Owner question: keep (request supersedes) or move to success (R0031 edits
  `_usePrecise`/`_runSetSearch`).
- A Reset apply that rejects (injected faults only) drops the owner: with the panel closed, recorded post-dispatch
  edits are not applied; with the dispatching panel open the form is repopulated from whatever runtime state the
  failed apply left, so I1 can be breached under that injected fault if `bindConfig` threw before binding.
- VM evidence uses the r0011 fixture's provider and renderer doubles; the window length is not measured; native
  cells use route stubs and a held detection, not real providers or real geolocation.
