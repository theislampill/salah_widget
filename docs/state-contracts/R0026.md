## Defects at the base

- **CF04 (coarse).** `coarseDetect` (config.js L230-270) parses with `parseFloat` (L235 GeoJS, L241 ipinfo:
  prefix grammar, arrays, `Infinity`), gates only null/NaN (L259), then `normalize()` (L260) clamps through
  `clampN` (L45, L113-114). GeoJS 999/999 becomes a successful acquisition at 90/180 and ipinfo is never tried.
  Non-numeric GeoJS `accuracy` becomes `NaN` (L238).
- **CF06 (forward).** `geocodeSearch` (L360-376): no HTTP gate for Nominatim (L369), per-provider and aggregate
  `.catch → []`, abort-only timer (L365) and no rejecting deadline; `_nomCands` `parseFloat` (L339), `_zipCand`
  `+p.latitude` (L348: `null`/`""` → 0), `_dedupeCands` drops only null/NaN (L355). Transport failure, HTTP 503,
  malformed/non-array body, timeout and a genuine no-match all return `[]`; partial coverage is invisible.
- **Consumers.** Builder `doSearch` (builder.html L300-310) and settings `_runSetSearch` (index.html L3923-3931)
  render "Couldn’t find" for every `[]` (builder L286, settings L3929). Builder `locate` (L437-449) publishes
  `pos.coords` unchecked; `SalahConfig.geolocate` (config.js L273-285, L279) also returns them unchecked.

## Owner decisions (2026-11-11, binding defaults)

- **A1** Zippopotam HTTP 404 on the supported postal lookup = valid no-match (provider OpenAPI spec). Not
  generalised to Nominatim, other endpoints, 429, 5xx or network failure; per-provider results stay explicit.
- **A2** Strict complete-value coordinate admission: finite JSON numbers and complete non-empty decimal strings
  (signed, fractional, surrounding whitespace trimmed). Reject null, booleans, arrays, objects, empty strings,
  Infinity, NaN, hex, prefix/trailing garbage; no partial `parseFloat`, no `Number()` coercion as the rule;
  exponent strings rejected (no supported provider is documented to emit them). Domains enforced BEFORE
  normalization. +0 and −0 preserved.
- **A3** One canonical detailed engine; `geocodeSearch` stays a documented, intentionally lossy array projection;
  builder and settings consume the detailed result. No second geocoder.
- **A4** Name `geocodeSearchDetailed`. Bounded result: not requested; matches (complete vs partial coverage);
  valid no-match; unavailable (transport/HTTP/parsing/timeout/admission); cancelled/superseded from existing
  consumer ownership. Candidate provenance and bounded provider attempt records; bounded `attempts` on coarse
  acquisition without breaking existing success fields. No raw responses, query histories or extra identifiers.
- **A5** Builder geolocation keeps its one-shot lifecycle and edit/session ownership; the same canonical
  admission helper applies at its result boundary before publishing, and in `SalahConfig.geolocate`.
- **A6** R000F-style consumer guards stay: a stale lookup's success or error cannot update the current form. No
  global cancellation framework or public token; cancelled/superseded is consumer-derived.
- **A7** Small controlled real-browser qualification on the generated application and builder (Chromium and
  Firefox): stubbed providers and geolocation only, never a real location or live provider request.
- **A8** R001E normalization/clamping for manual, hash and saved configuration is preserved. R0026 corrects
  admission of EXTERNAL provider evidence only.
- **A9** Concise truthful partial-coverage feedback; valid candidates stay usable; builder single-line tip and
  settings status, no new layout, no unnecessary provider detail.
- **A10** Dedup order and proximity policy preserved; the surviving candidate keeps its provenance; no rounding or
  synthetic accuracy.
- **A11** Absent/invalid/non-finite accuracy stays `null`, never zero; R0023 provenance and timestamps preserved.
- **Boundary.** Not implemented here: R0003's configuration-effect classifier, R000F's preview-ownership increment,
  any change to manual/hash/saved normalization, prayer selection (R0007), the web-font gate, weather eligibility
  (R000B) or retry spacing (R000D). Endpoints, request options and privacy boundaries unchanged.

**Admitted-location interface (for R0003 / R000F).** On `window.SalahConfig` (authored `src/native/config.js`):

- `admitCoordinates(lat, lon)` → `{ok:true, lat:number, lon:number}` | `{ok:false, reason:"latitude"|"longitude"}`.
- `geocodeSearchDetailed(query, {homeCC, timeoutMs})` → Promise of `{status:"not-requested"|"matches"|"no-match"|
  "unavailable", coverage:null|"complete"|"partial"|"none", candidates:[{lat, lon, name, norm, cc,
  provider:"Nominatim"|"Zippopotam", bounds}], attempts:[{provider, state:"ok"|"no-match"|"transport"|"http"|
  "parse"|"timeout"|"admission", reason:string|null}]}`. Provider failures never reject it; no query, body or raw
  text is in the record; nothing is persisted.
- `coarseDetect()` → the existing `{ok:true, cfg, source:"coarse-ip", provider, status:"ok"}` or
  `{ok:false, source:"coarse-ip", status:"failed"}`, both plus `attempts`. `cfg.lat/lon` are admitted values,
  `cfg.accuracy` is admitted or `null`; evidence stays R0023's `normalizeLocationEvidence` (unchanged).
- `geolocate()` → the existing success shape with admitted `lat/lon`, or `{ok:false, error, code}`.
- A selected candidate still becomes configuration through `placeLocationEvidence` + form + `normalize()`. R0003
  should compare that evidence (source/intent/provider/area/bounds/accuracy/acquiredAt), not coordinates alone.
- `cancelled/superseded` is consumer-derived: `doSearch` / `_runSetSearch` resolve `"superseded"` when the existing
  `ownsLookup` / `_ownsSetLookup` guard fails; form, feedback, pin and storage are untouched.
