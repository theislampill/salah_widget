## 2. M1 — refinement worker recovery (ISM-MOON-004, ISM-MOON-018)

Owner: `moon/src/moon-native.mjs`. No timer resource is added: the existing 4 Hz poll and the visibility handler
drive it, so the ES21-10 lifetime map is unchanged (dispose and construction unwind set the record to `idle`).

Dimensions: worker `none|booting|ready|rendering`; `recovery = {state: idle|scheduled|exhausted, attempts, limit 3,
nextAt, lastClass, outcome}`; document `visible|hidden`; disposal `live|disposed`; `bootCache force-cache|no-cache`.

| Event | Guard | Effect |
|---|---|---|
| `failed(error, class)` | not disposed | existing retention rule (keep only a still-matching surface); `unavailable`; error recorded; `bootCache='no-cache'`; then if `scheduled` already: nothing (no double schedule); else if class retryable and `attempts<3`: `scheduled`, `nextAt=now+[30 s,2 min,10 min][attempts]`; else `exhausted` |
| poll / visible transition | `scheduled`, not disposed, no worker, document visible, `now≥nextAt`, worker source present | `attempts++`, `start()` (new worker, boot with `cache:'no-cache'`) |
| hidden | — | nothing starts; the due attempt starts on the next visible poll |
| `start()` while `scheduled` (explicit `retry()`) | existing retry guard | `idle`; the driver attempt does not spend the automatic budget |
| refined `result` adopted | after any failure | `outcome:'recovered'`, state `idle` |
| `dispose()` / construction unwind | — | `idle`, `nextAt=null` |

Failure classes: retryable `boot` (worker boot-error incl. asset HTTP, size, identity, unhandledrejection), `crash`
(onerror, messageerror), `deadline` (120 s boot, 240 s render), `render` (worker render error incl. shard failure),
`transport` (file-entry chunk script unavailable), `start` (Worker construction or job post throws).
Deterministic, never retried: `contract` (result contract, linear-surface shape, calendar contract, nonfinite or
premultiplied surface, message contract, quality criterion not met) and `transport-identity` (offline chunk order,
embedded payload missing, chunk omitted its payload). Asset identity/size failures are retryable because a stale
cached body is a plausible cause and every recovery attempt revalidates.

Status truth: `status.status` is `unavailable` (never `paused`) while visible with a dead worker; `state.recovery`
is a plain copy read without `presentation()` being called for it.

Cache (ISM-MOON-018): `moon/src/moon-worker.mjs` `read()` admits only `force-cache` (default) or `no-cache` from the
boot message. `no-cache` makes the browser revalidate, so a heuristically cached 404 or a stale body cannot pin a
failure (RFC 9111 §4.2.2 permits heuristic freshness for 404 without `Cache-Control`); a 304 keeps the healthy
asset in cache. Healthy boots are unchanged (one `force-cache` request per asset).

## 3. M2 — initial-tier failure eligibility (ISM-MOON-005)

`status.initialError` stays the diagnostic record. Eligibility is `initialRetry = {count, notBefore, epoch, state:
idle|waiting|exhausted|permanent}`: a missing receiver or `SalahMoonInitialError` is `permanent`; a render throw
sets `count++`, `notBefore=now+60 s`, `epoch`; a re-attempt is allowed once per new epoch (`clear()`) or after
`notBefore`; the third throw makes it `exhausted` for the page. At most one re-attempt per eligibility event, never
per frame. `takeInitialHead` and the one-shot head retirement are unchanged. Diagnostics: `state.initialRetry`,
`state.initialEligible`.

## 4. M3 — fault-path presence (ISM-MOON-017, consequence of ISM-MOON-016; ISM-MOON-001) under DG-1 = B

Slot states: `presented(initial|preview|refined)`; `withheld(day | scene pending | no current presentation)`;
`unavailable(runtime absent)`. `updateSkySurface` is unchanged: it reveals only from a current runtime surface.

Construction failure (generated wrapper, `tools/build_moon.py`): the `moon-native` unit runs inside a
`try`; on a throw its own unwind runs (ES21-02/04/05/07 unchanged), then the wrapper records
`window.SalahMoonConstructionError`, installs `SalahMoonHead` with **no initial receiver** (so a night head
throws "Head Moon qualified initial unavailable" and presents no Moon that would then vanish), still calls
`SalahPrepareFirstPaint` (the sky first paint survives by day; at night the head reports its error and no first-paint
style is installed, as before), and rethrows the construction error (loud). The refinement tail is
`window.SalahMoonRuntime?.installWorkerSource(...)`: a no-op on an empty slot (no `TypeError`, EF-E04), while a
live runtime still throws on a source-identity mismatch and stays idempotent for a duplicate tail.

Natural-trigger census (DG-1 premise). Statements that can throw while the wrapper constructs:
`moon-install-guard` (replay refusal, by design, never on a fresh page); the initial decode (already caught into
`SalahMoonInitialError`); in `moon-native` before its `try`: `SalahMoonRuntime?.dispose()` (idempotent),
`new URL(…, script.src || document.baseURI)` (throws only for a non-hierarchical base such as a `data:` or `blob:`
document; every supported entry has an http(s) or file base, and `offline.html` takes the embedded branch without a
URL), `createElement('canvas')`, `startMoonDetail()` (a null 2D context is tolerated); inside the `try`:
`addEventListener`, global assignment, `setInterval`, `requestAnimationFrame` (all present in the three supported
engines). **No natural trigger was demonstrated**; the only construction failures on record are injected (R0021
§D, and this work order's `construction` cell). Option C was therefore not investigated (owner rule). Generic
resource exhaustion could throw anywhere and is not a demonstrated trigger.

## 5. M4 — light eligibility bound to the presented surface (ISM-MOON-020)

Predicate (runtime, `moon-native.mjs`): `presentable` is true iff `matches(accepted,s)` or a queued preview
matches `s`, computed from `capture()` with no `presentation()`, `adopt`, `syncTexture` or `publish`.
Native gate (`src/native/index.html`): `moonSurfacePresentable() = presentable ∧ .mphoto href ∧ _skySceneKey≠null`
(never `surface()`, `state`, `detailEnabled` or `request()`); `lunarPresentation` passes `!presented` as
`surfaceFailed`, so every consumer (sky lift, cloud light, local wash, beam, glow, halo, corona, paraselenae,
`debugOptic` lunarhalo/paraselene) is zero with reason `surface-unavailable` without a presented surface. The R0022
reasons near-new, below-horizon and daylight keep priority order after it. `_pbrFailed` is retired as a light
input; it still drives only the dormant legacy renderer. The calendar disc's opacity never depends on it.

Asynchronous changes: `SalahMoonHost.publish`/`fallback` call `noteMoonSurfaceChange()`, which marks
`_renderDirty` only when the predicate differs from the value the last `lunarPresentation` used (no render loop), and
re-marks it in a microtask (loader turns clear the flag after their render). `commitSkyScene` refuses to commit a
frame whose decision changed during its paint (marking a render); the consistent next render commits, so no
unlit-then-lit transition is ever committed and animated. `paintCelestialWithoutTimetable` (the no-timetable
path, which computes light before its own `request()` and is not covered by the commit guard) repaints its one
lunar light property when that request changed the decision, then reveals. Together: the Moon and its moonlight
appear in the same visible frame. (A reveal gate in `updateSkySurface` was tried and withdrawn: it was not needed
once the no-timetable repaint existed, and it broke the accepted R0003/R0011/R0021/R0025 surface-bound reveal and
mask contracts, which reveal from the surface alone.)
This was found by native startup probes (§7) after the first implementation; the one-line addition sits in the
function R003A also edits (coordination note).

## 7. Whole-scene coherence (owner design standard, 2026-11-15)

Healthy scenes (day, twilight, night; clear, cloudy, precipitating): no change in steady state (R33-17: 0 differing
pixels main vs branch, 15 scene×engine cells and 15 Moon crops). The only healthy-path timing change is at the
start of each sky scene at night: the scene commits one render later, when its lunar light already matches the
presented surface, so moonlight never fades in after the reveal. By day the decision is the same before and after
the paint (no surface, darkness 0), so day scenes commit as before.

Transitions this change can trigger, and what a viewer sees (native frame sequences, 125 ms cadence, Chromium,
Firefox, WebKit; artefacts kept in the worker scratch, not committed; recipe `tools/qa/r0033_native_cells.cjs`):
- **Healthy night startup**: the first implementation revealed the disc 130–310 ms before its moonlight on the
  no-timetable path, then the sky brightened in one step (probe: moon-ready with `--moonbeam` 0.000, then 0.405;
  main had no gap). Corrected (§5); the final tree matches main on all three engines (lit from the first revealed
  frame).
- **Worker failure → `exhausted`**: no visible change. The initial V5 disc and its light stay (a still-matching
  surface is retained); only `state.recovery` changes.
- **Recovery attempt**: no visible change while the new worker boots.
- **Recovery success**: the terrain preview replaces the initial tier through the existing preview/result path
  (unchanged by R0033; the same swap a healthy page makes once). Measured: 4,420 Moon pixels change in one frame,
  maximum channel delta 27/255 (Chromium); light unchanged (0.405 throughout). Finding F-2.
- **Construction failure (startup)**: the card reveals with no Moon and no moonlight; nothing appears and then
  vanishes. Stars fill the Moon's corner. This is the documented DG-1 = B exception.
- **Surface withdrawal while presented** (texture or adoption fault, M7): `moon-ready` is removed, and
  `.c:not(.moon-ready) .moon{visibility:hidden}` hides the disc in one frame while the light consumers fade out
  over their CSS transitions (beam 1.4 s, sky colours 1.1 s) and the star cutout drops after its 1.2 s delay. That
  is an abrupt disc disappearance for a software fault (finding F-1, §9).
