## 2. Gate machine (`.github/workflows/qualification.yml`, `tools/qualification/qualification_gate.py`)

**Identity.** One run per pull request head, push or dispatch. **Authority.** The checked-out commit; the R0028
population manifest and ledger for suite verdicts; the R0029 builder for parity.

**Triggers.** `pull_request` to `main`; `push` to `main`; `push` to `claude/r002a-*` (pre-merge qualification
of this work order and its fault-injection branches only; inert once those branches are deleted);
`workflow_dispatch` (effective once the file is on the default branch).

**Binding (I2).** `GATE_SHA` is the pull request head SHA (`github.event.pull_request.head.sha`), not the
ephemeral merge ref, or `github.sha` for pushes and dispatches. Every job checks out exactly `GATE_SHA`; every
receipt records `head`, `tree`, `GITHUB_SHA`, event, run id and attempt; artifact names carry `GATE_SHA` and the
attempt.

**Jobs, verdicts and exits.** Each job is `qualification_gate.py <job> --out <new dir>`: it writes
`<job>.json` and `<job>-summary.md`, appends the summary to the job summary, emits a `notice`/`error`
annotation with the verdict and prints `VERDICT <string>`. Exit 0 for `PASS`,
`PASS_WITH_DECLARED_FAILURES (n)` and `PASS_WITH_DECLARED_DIVERGENCE (n)`; exit 1 for `FAIL` and `INCOMPLETE`.
A GitHub check has no third colour, so a declared verdict is a green check whose verdict string (summary,
annotation, receipt) is never a plain PASS (I3). A certificate quotes the receipt verdict, not the colour.

| Job | Runs | Red when |
|---|---|---|
| J1 `parity` | `python tools/build_native.py` twice in the disposable checkout (fetch-depth 1, Python 3.11) | a build exits non-zero or prints no JSON report; `git status --porcelain --untracked-files=all` is non-empty; `git diff --exit-code` fails; the second build reports `written` or `removed` > 0 |
| J2+J3 `suites` | `python tools/cp9/run_native_regressions.py --output <dir>/runner` over the whole registered population (fetch-depth 0, Python 3.11, Node 24.14.0) | runner verdict `FAIL` or `INCOMPLETE` (any undeclared failure, unexpected pass, absent ledgered case, setup error, unregistered instrument, abort or source change), or a runner exit code that disagrees with its verdict |
| J4 `v1` | `tools/verify_v1.py --negative-control` and `--check-pages` (R0037 repaired `--check-pages`, so it joins J4 per issue §8) | either exits non-zero |
| J5 `pins` | (a) docs-receipt pins; (b) README review-first installer pins (sparse, treeless history) | section 2.5 |

**J2/J3 partition.** The runner is invoked once (one census, one ledger adjudication). The receipt partitions its
command rows by launcher: J2 = node instruments (the node glob, the `.test.mjs` glob, the docs contract, mutation
suites, `tests/real-sky`, `moon/tests`); J3 = Python launches (unittest groups including the builder, transform,
Moon-guard and R0029 generator tests, the runner's own contract, and the vendor scientific runner). Each part
gets its own verdict with the same rules as the runner's `summarize`; setup errors make both `INCOMPLETE`. Every
Python test cited as gate evidence is a registered population entry: an unregistered instrument is a runner setup
error.

**Condition-gated entries (R28-L12, L14, L17).** The runner probes `symlink-unavailable`. Where symlinks work
(the Linux runner) these entries are inert and their cases must pass; the suites receipt lists, for every
condition-gated active entry, whether the condition holds and what was observed ("case passed (entry inert on
this host)", "declared", or "case did not pass: …").

**Guards.** `permissions: contents: read` only; no `secrets.` reference; `persist-credentials: false` on every
checkout; every job and every step has `timeout-minutes`; actions pinned by commit SHA (`actions/checkout`
`3d3c42e5…` v7.0.1, `actions/upload-artifact` `ea165f8d…` v4 as in the existing workflows; `actions/setup-python`
`5fda3b95…` v7.0.0 and `actions/setup-node` `82076278…` v7.0.0, resolved by read-only `gh api`). Network: the
checkout, the pinned action downloads and the toolchain downloads those actions make. Temporary directories are
under `$RUNNER_TEMP`; the runner binds each child's `TMP`/`TEMP`/`TMPDIR` inside its receipt.

**Concurrency.** `group: gate-${{ github.ref }}-<'pr' for pull requests, otherwise github.sha>`,
`cancel-in-progress` only for pull requests. This deviates from the issue's literal `gate-${{ github.ref }}`: with
one group per ref, GitHub cancels *pending* runs in the group even without `cancel-in-progress`, which would drop
results on `main`. Per-SHA groups keep every push's result.

**Effects (I4).** Check results and receipt artifacts (14-day retention; the runner's per-command `tmp` trees are
excluded). Nothing is written to the repository; no deploy, push, comment, status write or settings call.

**Invariants.** (I1) a new failing case, abort, unexpected pass, dirty rebuild or v1 change is red; (I2) a result
binds the exact head SHA; (I3) declared verdicts are never reported as plain PASS; (I4) the gate cannot deploy,
push or comment (read-only token, no write step).

**Recovery.** Re-run. A flaky instrument is fixed or ledgered under R0028's rules (exact command and case, reason,
owner). Retry-until-green is forbidden: the workflow has no retry loop.

## 3. Delivery-identity machine (`tools/qualification/delivery_identity.py`, `.github/workflows/delivery-identity.yml`)

| Element | Implementation |
|---|---|

**Routed finding for R0028 (issue 89): stale bytecode in the runner-mutant harness.**
`tests/test_regression_ledger.py` `test_runner_ledger_mutants_fail_their_named_controls` rewrites one module path
(`tools/cp9/run_native_regressions.py` in a temporary root) once per mutant and runs it in a fresh interpreter.
`census-blind` and `glob-pin-ignored` both insert `[] and `, so the two mutated files have the same size. On a fast
host both rewrites fall in the same second. CPython validates a cached `.pyc` by source size and whole-second mtime,
so the second mutant can execute the first mutant's bytecode, and `glob-pin-ignored` "survives".

Evidence:
- run 43419734052 (bytecode cache on): `AssertionError: 0 == 0 : glob-pin-ignored survived`;
- run 43421970001 (`PYTHONDONTWRITEBYTECODE=1`, nothing else changed for this instrument): the instrument PASSes.

The gate contains it by setting `PYTHONDONTWRITEBYTECODE=1` for every job. Without that, a mutation control would
pass only on one OS. Suggested repair, for R0028's owner and not made here because the accepted test is outside
issue 91: in that test, run each mutant with `-B` or `PYTHONDONTWRITEBYTECODE=1` in `execute()`, or write each mutant
to a distinct path.
