## C08: discovery to action

Each target retains its browser/profile identity, existing positive flags and
matches, and explicit discovery knowledge. Eligibility is derived from that
knowledge at preview, pre-staging selection and actual dispatch. There is one
eligibility rule, no force override and no artifact-readiness rule in discovery.

| Discovery status | Evidence meaning | Derived eligibility |
| --- | --- | --- |
| `known-new` | Supported inventory positively identifies TablissNG and no legacy match | `eligible-known` |
| `known-neither` | Supported complete inventory contains neither detector match | `eligible-known` |
| `known-legacy` | Supported inventory positively identifies legacy Tabliss | `legacy-refused` |
| `known-both` | Supported inventory positively identifies both | `legacy-refused` |
| `unknown` | Inventory cannot establish a supported complete result | `unknown-held` |

An existing positive legacy flag always takes precedence and produces
`legacy-refused`, even if incomplete evidence leaves the overall status unknown.
This preserves conservative no-Python and partially parsed legacy hints. Existing
TablissNG skips extension acquisition but still uses the ordinary manual preset
handoff for an eligible target.

Firefox metadata must be a JSON object with an `addons` array. An explicitly
empty array is a supported empty inventory. Every nonempty element must be an
object; supported `id`, `name` and `defaultLocale.name` fields must be strings or
null, and `defaultLocale`, when present, must be an object or null. At least one
supported identity string in each element must contain a non-whitespace
character. Unknown unrelated properties do not make an empty identity usable.
The existing textual match policy is retained; this change does not certify an
extension's publisher, signature, browser compatibility or installation health.
PowerShell also checks the original JSON root token because its JSON command can
enumerate a singleton top-level array into an object. Such an array remains an
unsupported shape even when its one element resembles valid metadata.
Recognized Firefox property names are case-sensitive. PowerShell explicitly
checks the original names of `addons`, `id`, `name`, `defaultLocale` and its
`name` field before using member lookup. Wrongly cased aliases are unsupported
metadata and cannot certify absence or a new installation.

JSON syntax and property identity are checked before inventory classification.
Bash rejects duplicate object keys and non-JSON constants through its standard
JSON parser hooks. PowerShell's `Test-StrictJson` validates contiguous JSON tokens
and object/array grammar before the permissive host conversion. It requires
proper separators, closing containers and one complete root; comments, single
quotes, bare keys, trailing commas and invalid numeric/string tokens are rejected.
Decoded object-key sets detect escaped duplicate names. PowerShell additionally
rejects case-insensitive key collisions because its downstream object property
lookup is case-insensitive. The validator operates only on in-memory text and
does not compile code, load an external package or perform external effects.

Malformed JSON, unsupported shapes, insufficient identities, unreadable or
absent metadata and decoding failures produce explicit unknown reasons.
Unsupported entries do not terminate discovery of other profiles. Positives
found before an unsupported entry remain conservative hints, not proof of a
complete inventory. Bash without Python uses independent positive text searches
for new and legacy identifiers, returns `unknown` even with no text match, and
warns on the diagnostic stream. It never promotes a grep-negative result to
known absence. An interpreter execution failure also becomes an unknown target.

Chromium retains its existing detector scope: Bash checks known extension
directories; PowerShell retains its directory and Preferences text checks.
Derived states describe that scope only. An installed browser root or executable
without a discovered profile is `unknown` with reason `no-profile`.

## Structured records and consumers

Bash `firefox_status` emits exactly one newline-terminated seven-field record:

```text
hasNew|hasOld|escapedMatches|status|reason|evidenceClass|metadataSource
```

Metadata match text escapes percent, pipe, ASCII control and DEL bytes with
percent notation. This preserves Unicode and prevents text inside metadata from
becoming a record delimiter or terminal control. Diagnostics use stderr. A
metadata path containing pipe, newline or carriage return cannot be emitted as a
safe record and is reported as unsupported.

`add_target` appends four fields to the original thirteen, preserving the old
field order. The complete target record is:

```text
index|key|label|family|profileName|profilePath|exe|hasNew|hasOld|matches|store|manager|newtab|discoveryStatus|discoveryReason|discoveryEvidence|discoverySource
```

All five actual target reads consume the full record: menu, preview, selection
validation, pre-staging eligibility counting and action dispatch. `add_target`
rejects delimiter-corrupt records. Profile producers read `find -print0` output
before emitting their retained line protocol so embedded newlines cannot alias a
different existing profile. Newline/carriage-return paths are excluded with a
warning; this is explicit refusal, not support for those filenames. Spaces,
Unicode, literal backslashes and an unterminated last producer line remain
supported by the actual detector consumer. Profile arrays and counts are reset
for every browser configuration.

PowerShell `Get-FirefoxExtensionStatus` returns one object with retained
`HasNew`, `HasOld`, `NewMatches`, `OldMatches`, plus `Status`, `Reason`,
`EvidenceClass` and `MetadataSource`. `Get-Targets` copies these to
`DiscoveryStatus`, `DiscoveryReason`, `DiscoveryEvidence` and `DiscoverySource`.
The original `Config`, browser/profile fields, indices and positive flags remain.
Diagnostics do not enter the object pipeline.

Stable reasons currently include `supported-metadata`, `metadata-absent`,
`metadata-unreadable`, `metadata-malformed`, `metadata-encoding`,
`metadata-unsupported`, `parser-unavailable`, `parser-failed`,
`profile-path-unsupported` and `no-profile`. Chromium uses its own retained scope
reason and evidence class. Reasons identify the failed capability or evidence
boundary without reproducing parser exception text or metadata contents.

## Selection, preview and handoff

Both entry points display knowledge and held/refused status. Default-all and
explicit selection use the same derived eligibility. Counts report eligible,
held and refused selected targets. A held or refused target never reaches
initialization, download, extraction, clipboard, browser opening or preset import
dispatch. Independent known safe peers remain usable.

No eligible selected target yields a nonzero exit before staging. A successful
eligible setup reports manual actions pending; acknowledgements are user input,
not evidence that a browser installed or imported anything. Profile metadata is
only read. Discovery does not modify, repair or delete browser profile storage.

Offline preview uses the same target knowledge and returns before normal staging
or terminal acquisition. It performs local discovery and prints unresolved plans;
unknown and legacy targets cannot become usable artifact paths. This preserves
the R0016 early-return interface and its separate effect-free acceptance work.

## Discriminating evidence

`tests/install-discovery.py` invokes the actual Bash parser, actual target builder
and complete installer entry. Complete-entry tests reuse the contained terminal
fixture; only external boundaries are intercepted. Cases cover supported empty,
new, legacy and both inventories; absent/unreadable/malformed/invalid-encoding
metadata; unsupported root, collection, item and localization shapes; insufficient
identities and useful identity-field controls; no-Python positives and negatives;
partial legacy hints; metadata delimiters; profile record identity; default-all,
explicit, mixed and zero-eligible choices; and preview snapshots/effect logs.
The no-Python mixed preview includes an independently eligible Chromium profile.

`tests/install-discovery.ps1` invokes actual AST-extracted parser and builder
functions and exact main-body bytes in a private child process, with controlled
staging, transport, clipboard, opening and prompts. Native full-file loading and
platform discovery remain separately exercised by the existing entry harnesses.
Its `SourceFile` argument binds the exact candidate. A Linux PowerShell execution
is supplemental language/.NET evidence only.

`tests/install-discovery-mutations.py` first requires the exact candidate's named
assertions and paired empty/new healthy controls to pass. Each syntax-valid
mutant must fail all designated behavior assertions while those controls still
pass. Mutants cover absence/catch-to-absence, dropped builder knowledge, admitting
unknown in default-all, both becoming safe-new, no-Python negative promotion,
omitted held summaries, diagnostics corrupting the structured stream,
insufficient identities becoming absence, and newline aliasing in Bash.
PowerShell additionally mutates the singleton-root-array guard, strict-validation
call, duplicate-key guard and trailing-separator transitions. Bash mutates its
duplicate-key and non-JSON-constant parser hooks. Empty, new-extension and complex
valid JSON controls remain healthy for every mutant.

Affected retained fixtures now explicitly create `{"addons":[]}` for healthy
Firefox profiles. Bash harnesses accept `SALAH_TEST_BASH` (default `/bin/bash`),
resolve temporary roots physically, and use platform-correct browser roots.
The pipe/PTY entry executes that same shell for the complete script. The native
Windows driver accepts `INSTALL_TEST_PS7` and the selected runtime's adjacent
Modules directory without changing the Windows PowerShell 5.1 host.
