## 1. Machine RA — radar acquisition (ISM-WX-004), D-32-1 = A2

**Enablement.** `const RADAR_ACQUISITION=Object.freeze({enabled:false,reason:…})` and
`radarAcquisitionEnabled()` (`RADAR_ACQUISITION.enabled===true`). No URL, fragment, query or configuration field
reads or writes it (source search in `tests/radar-acquisition-scope.test.cjs`).

**Product entry.** `fetchRadar()` is now the gate: `if(!radarAcquisitionEnabled()) return; return acquireRadar();`.
It is evaluated before `retryGate("radar")`. The three product callers (boot, `startWeather` on boot/apply, the
loop poll) are byte-unchanged, so the accepted assertion that pins the poll line
(`tests/weather-renewal-state.test.cjs`) and every harness that stubs `fetchRadar` stay valid.

**Retained path (test-only).** The former acquisition body is `acquireRadar()`, unchanged apart from admission:
`retryGate`, N03 request ownership, the 600 s spacing, the 10 s manifest and image attempts, the timestamp rules
and `radarEvidence` are as before. How tests still exercise it: the r000c source fixture binds
`fetchRadar: acquireRadar` when it exists (an explicit opt-in, one line in `tests/r000c-weather.test.cjs`), so
`r000c-weather`, `r000d-weather`, `r000b-remaining`, `r0024-weather` and `weather-retry-clock-*` drive the same
path as before; the native weather control `tests/weather-native/native-controls.js` opts in the same way.

**States.** enablement {off(reason)} (on exists only for harnesses calling `acquireRadar`); manifest {fetching,
body, settled}; tile index {valid, rejected}; host admission {admitted, rejected(reason)}; image {loading,
decoded, failed}; sample {none, available, stale}.

**Guards on the retained path (order).** finite frame/index seconds (unchanged) → tile index
`radarTileIndex(lat, lon, 6)` → host and frame-path admission `radarTileBase(host, path)` → image attempt.

- Tile index (CI-05): longitude outside [-180, 180] (or non-numeric) → rejected; longitude +180 is the same
  meridian as -180 and wraps to column 0; any row or column outside [0, 2^z) — latitude beyond about
  ±85.0511°, or a pole — → rejected. Reason `radar tile index outside Web Mercator`.
- Host: the manifest `host`, with one optional trailing `/`, must equal an allowlisted origin. The allowlist is
  `["https://tilecache.rainviewer.com"]`. **Source: repository fixtures only (`tests/r000c-weather.test.cjs`,
  `tests/r000d-weather.test.cjs`); unverified against the provider** (no provider document was read or
  contacted). Exact matching rejects other schemes (`http:`), hosts and suffix hosts, userinfo, ports, paths,
  queries, fragments and protocol-relative forms. Reason `radar tile host not admitted`.
- Frame path: one segment `/v2/radar/<id>` with `<id>` in `[A-Za-z0-9._-]`, never `.` or `..`. Absolute,
  protocol-relative, dot-dot, query-bearing, relative and other-prefix paths are rejected. Reason
  `radar frame path not admitted`.
- A rejection writes `wxAttemptState(op,a,"rejected",reason)` and dispatches no Image. A manifest with a missing
  host now settles `rejected` too (previously it returned silently with state `received`, part of PRA-F-15,
  owned by R0036): this is the host-admission reason the issue's §D.1.12 requires, not a change to other
  outcome records.

**Postcondition.** `qaState().wxTruth.radarSource` = `none (radar acquisition disabled in the product)` and
`wxTruth.radarAcquisition` = `{enabled:false, reason:"disabled in the product (R0032 D-32-1 A2; retained for tests only)"}`;
`requests.radar` stays `null` in the product. These are pure reads (R0036 audits qaState later).

**Invariants.** I1 radar grants no precipitation, lightning or display authority (`radarPrecipNow()` is 0; no new
consumer). I2 no location-derived tile request to a non-allowlisted origin, and none at all in the product.
I3 weather acquisition is independent of radar enablement (weather requests continue in every product phase).

## 2. Machine EL — legacy site elevation (ISM-WX-008)

`siteElev` keeps its value; `_siteElevAt={lat,lon}` records the coordinates of the response that carried it
(the writer's captured request coordinates, same eligibility as before). Readers (`altClarity` in the atmosphere
and the `&debugLayers=1` read-out) use `siteElevation()`: the value while `lat/lon` equal `_siteElevAt`, else the
documented default 0 m.

- P1 a value admitted for A is never read while the current coordinates are B ≠ A.
- P2 a broad change at unchanged coordinates (units, method) keeps the value.
- P3 before any admission for B, readers see 0 m.
- P4 the CP9 `acceptedElevation` lease (`real-sky/native-host-hooks.js`) is untouched.
- Binding rule A → B → A: the slot holds the last admitted value only. If B never admitted, A's own value is read
  again at A immediately (it was admitted for A). If B was admitted, A reads 0 m until A is re-admitted.

## 3. Machine CR — per-location cache retention (ISM-CFG-002 / ISM-WX-001), D-32-2 = B, D-32-3 = A

States per stored key in the prefix-exact namespaces `salah:` and `salahwx:`: {protected, usable-other, expired,
unreadable}.

- **Protected** (never removed, whatever their age): `cacheKey()` with the current `_cacheTz` and `wxKey()` — the
  exact keys boot may read for the current configuration. A stale (wrong-day) record under the selected prayer
  key survives (README: it may resolve the zone).
- **Unreadable**: prayer — no admissible record (`recordObject` + `admitPrayerRecord`, the same rules as
  `readPrayerCache`) or invalid JSON; weather — invalid JSON or no numeric receipt `ts`.
- **Expired**: weather receipt outside the `loadWx` window (`now - ts >= 6 h`) or in the future; prayer record
  dated before UTC civil day − 2 (no zone, UTC−12…+14, can hold such a date as current or next).
  Future-dated prayer records are kept (device-clock skew is not evidence).
- **Never touched**: other prefixes (including `salah_widget:*`, V1's `salah_widget:v1:*`, `salah_widget:config:v1`,
  look-alikes `salah`, `salahwx`, `salah-…`).

**Trigger and bound.** `evictUnusableLocationCaches()` runs at most once per document (`_cacheEvictionRan`),
called only after the first successful fresh cache write — `saveCache` after its `setItem` succeeds, or the
weather write in `fetchWeather` — never on the boot selection path, which still reads only the selected keys and
neither enumerates nor deletes. At most 256 removals per pass.

**Effects and failure.** Keys are enumerated first; each candidate is read, classified, re-read and removed only
if its bytes are unchanged (a concurrent writer's fresh record is kept). Every storage exception is contained
per key and for the whole pass; an exception never escapes into the write or the display. The pass changes no
in-memory state, so the current session's display is identical with and without it.

**Reset (D-32-3 A).** Reset is unchanged: `SalahConfig.clearLocal()` removes only `salah_widget:config:v1`; the
caches survive. No Reset path was added; any future Reset integration belongs to R0030's single Reset transition.

**Residuals.** A cross-tab writer between the re-read and `removeItem` can still lose a fresh record (narrowed
to one synchronous step; the cost is one cache miss). Usable entries for other locations persist until they
expire and a later page load's pass removes them.

### 6b. Whole-scene coherence (design standard, information truth)

Disabling radar acquisition changes no rendered weather in any scene: radar granted nothing (no header text,
label, `data-*`, particle, cloud, optic or permission read `weatherRadar`; `radarPrecipNow()` was already 0), so
day, twilight and night, clear, cloudy and precipitating scenes and their transitions (renewal, location change,
long idle, preview) are unaffected; the healthy-scene pixel control above confirms it. The elevation binding
changes pixels only in the A → B window before B's weather is admitted, and only toward the value a cold B load
shows (a small haze/star-visibility term). Cache eviction changes no in-memory state and no displayed value.
What does change is information truth: the README recipient table, credits and builder note now say that the
current widget sends nothing to RainViewer, which is exactly what the product does.
