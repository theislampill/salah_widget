### 1.1 ISM-PRAY-004 — rollover, prefetch, cooldown and stale state (made explicit; behaviour unchanged)

| Dimension | Values | Owner |
|---|---|---|
| current record | ready (`prayerRecordReady(today, civil day)`), stale (`today` exists for another day or zone), absent | `adoptPrayerBundle`, `maintainPrayerDay`, `resetForNewLocation` |
| current recovery | idle, owned (`_requestSlots.current`), cooldown (`_prayerCooldown.current = {day, nextTry}`) | `beginPrayerRequest` / `finishPrayerRequest`, `loadPrayerData` |
| prefetch | idle, owned (`_requestSlots.prefetch`), cooldown (`_prayerCooldown.prefetch`), tomorrow ready | `prefetchPrayerDay` from the prayer stage of `render` |
| mirrors | `fetchingTomorrow`, `_rolloverBusy`, `_rolloverNextTry` | written beside the slots and cooldown; read by `qaState` and test harnesses only |

| Event | Guard | Effect |
|---|---|---|
| loop frame (`maintainPrayerDay`) | civil day resolved, coordinates present, current not ready | promote an exact `tomorrow`; else adopt an exact cache for the zone |
| same | `tomorrow` not ready for the next day | drop `tomorrow`, dirty |
| same | — | `_prayerStale = !!today && !ready`; dirty on change |
| same | not ready and `_requestSlots.current` free | `loadPrayerData` → `beginPrayerRequest("current", day)`: refused while the same day's 60 s cooldown runs (elapsed clock) |
| prayer stage of `render` | current ready, `tomorrow` not ready, slot free, cooldown elapsed | `beginPrayerRequest("prefetch", next day)` |
| successful adoption of a new civil day | — | `_prayerStale=false`; a current cooldown for an earlier day restarts at `{day, nextTry:0}` |
| broad configuration change | — | `beginRuntimeGeneration` (slots and cooldowns cleared, attempts aborted) then `resetForNewLocation` (records, mirrors, stale cleared) |
| `SalahClock.set` | valid control | `maintainPrayerDay` then `render` |

Invariants:

- **I-S1 `_prayerStale ⇒ model() === null`, as amended (R002E-A2): it holds except in one clock-step-back interleaving,
  which is documented and retained.** It holds over every sequence in E-02 (forward and backward day jumps between
  frames, a three-day jump, failed rollover through its retries, clock seeks, prefetch promotion, broad apply while
  stale, zone change). **Exact reachability condition:** ordinary wall mode only (anchored clocks use the elapsed
  clock); the device wall clock steps back across civil midnight between `maintainPrayerDay()` and `render()` inside one
  loop frame, while the record is still current for the earlier day and `tomorrow` cannot be promoted.
  `maintainPrayerDay` classifies the record stale for the later day; `render` reads the earlier instant, finds the
  record current, publishes the model and writes `data-stale="prayer"`; the next frame's `maintainPrayerDay` clears
  `_prayerStale` and its render writes `""`. The rule and writer are retained unchanged (G-E1, §3); the E-02 row
  "retained stale marker is reachable only in one clock-step-back interleaving" pins this behaviour.
- **I-S2 mirrors equal the authoritative state (enforced by test, option (b)).** At every quiescent point:
  `fetchingTomorrow === (_requestSlots.prefetch !== null)`, `_rolloverBusy === (_requestSlots.current !== null)`, and
  while `_prayerStale` is true `_rolloverNextTry === _prayerCooldown.current.nextTry`, so `qaState().cache.rolloverPendingMs`
  is the remaining current cooldown. Outside the stale state `_rolloverNextTry` may keep an earlier begin's value
  (a day-change adoption restarts the cooldown record without touching the mirror); no reader observes it there.
- Civil midnight is an ownership event; a next-day record cannot change the present zone (R0005/R0006, unchanged).

Diagnostics: `qaState().cache.prayerStale` and `rolloverPendingMs` keep their names and derivation (E-05).

### 1.3 ISM-PRAY-007 — countdown name fit cache

The fit key is `currentKey | round(sunrise) | round(sunset) | noon | decl | selection.generation | font signature`.
`noon`, `decl` and the day length are the model's determinants of the rail; latitude changes only through a broad
configuration change, which begins a new runtime generation, so the generation component invalidates the fit on
every location change. The font gate (R0007: `cnFontChanged` clears the key) and the exact-`d` sample cache are
unchanged.

**Key completeness (coordinator item 4).** Every input `fitCn` reads, and why each is keyed or cannot change the fit:
the name text, sunrise, sunset, noon, declination, generation and font states are keyed. The rail's other input is the
per-render "now" knot; the `.nt` box enters only through its vertical midpoint; the horizon is the fixed SVG line
`y=104` of a fixed 180 px arc; the bar follows the arc in flow with a fixed margin; `.foc` is absolutely positioned at a
fixed top; and every output is computed from differences of these positions, so a translation of the whole panel (for
example by the weather information line or the header) cancels. Appearance, the header label and the `.left` text do not
enter the fit. Measured with `node tools/qa/r002e_fit_discriminator.cjs --inputs` (three scenes × three engines,
in-place refits with the key cleared, [report](evidence/R002E/fit-inputs-candidate.json)): varying the `.nt` text
(`—`, `15:30`, `3:30 PM`), the "now" knot (three clock seeks inside one current period), appearance (contrast/glass),
the `.left` text and the header label moves the fit by at most 0.01 px (top) and 0 px (font-size, margin) — within the
issue's bounds. Decision: no input that changes the fitted geometry beyond the bounds can change without changing the
key; nothing further is keyed. Not covered: arbitrary embedding transforms or page zoom (the card is a fixed 325×530
CSS-pixel layout; the constants `M` and the gap are CSS pixels), recorded as before in ISM-PRAY-007.

## 4. Deviations from the issue (recorded)

1. **Fit key uses the rail's determinants, not the exact `d`.** The rail `d` contains the per-render "now" knot
   (`drawArc` inserts `nowAbs` as a vertex), so keying on it would refit on every render.
2. **Broad location changes invalidate the fit through the generation in the key, not by clearing `_cnFit` in
   `resetForNewLocation`.** Several accepted fixtures (`tests/r0003-harness.cjs` and others) evaluate
   `resetForNewLocation` without the fit region, where `_cnFit` is undeclared; every broad change also begins a new
   generation, which the key carries. Mutant m3 is accordingly "key without the generation".
3. The E-02 property test found the stale marker reachable in one interleaving; the Andon was raised and G-E1 was
   resolved by retention (amendment R002E-A2), so rows E-01/E-02 are measured against the amended wording.
4. Two-site pairs use same-meridian sites (§2); the issue's Madinah/Makkah example never coincides.
