## 1. Implemented contract

### 1.0 The stage boundary and the fault record (D.4)

- `runRenderStage(name, fn)` runs `fn`; on a throw it calls `recordRenderFault(name, error)` and returns `false`.
  No retry inside a frame, no timer, no backoff: the next frame runs the stage again from scratch.
- `recordRenderFault` keeps **one bounded in-memory record per stage name**: `{count, first:{at,message},
  last:{at,message}}`, frozen, message truncated to 200 characters, `at` = rounded `performance.now()`. No stack is
  kept; nothing is stored or sent. The first occurrence of each distinct stage+message (at most 32 distinct keys per
  page life) is reported once through `reportError` (so Playwright `pageerror` and the console see it), falling back
  to `console.error`; repeats are counted, not re-reported.
- Within one `render()` call the same error object is recorded once (inner owner first): `applyTheme` records
  `theme-<stage>` before its retained rethrow, and the caller's boundary does not count it again.
- `qaState().renderFaults` is a frozen copy of the record (a pure read; `null` in isolated fixtures without the
  render owner, like the other best-effort readouts). No user-visible indicator is added; no second Moon-presence
  owner is created (R0033 owns Moon slot presence under failure).

Stage names: `prayer`, `prayer-withdrawal`, `weather-sync`, `weather-decision`, `weather-header`,
`weather-withdrawal` (no-timetable cloud reconcile + effects withdrawal, one stage — see §4), `celestial`,
`moon-geometry`, `stars`, `theme-atmosphere`, `theme-paint`, `lightning`; loop: `prayer-day`, `render`,
`cloud-publication`, `clouds`, `telemetry`, `sky-preview`, `frame` (residual); boot/apply/clock: `sky-scene`,
`scene-build`, `moon-geometry`, `moon-invalidate`, `moon-handoff`, `sky-preview`, `real-sky`, `render`,
`weather-header`.

### 1.1 ISM-PRAY-010 — render loop (D.1)

| Dimension | Values |
|---|---|
| `started` | `_loopStarted` false → true once (unchanged) |
| `scheduled` | `_raf`: `null` or the one pending frame id |
| `frame` | `_running`: idle / running |
| `wanted` | `_wanted`: true after `start()`, false after `stop()` |
| `visible` | `_onScreen` and `document.visibilityState` (unchanged) |

| Event | Guard | Effect |
|---|---|---|
| frame begins | — | `_raf=null` (the id is consumed), `_running=true` |
| frame body | simulation ready | `prayer-day` → weather/radar poll (async, unchanged) → `render` on a new second or dirty → `cloud-publication` → `clouds` → `telemetry` → `sky-preview`, each in a stage boundary; a residual throw is recorded as `frame` |
| frame ends (`finally`) | `_wanted` | `_running=false`; schedule exactly one next frame, however the body ended |
| hide / offscreen (`stop`) | — | `_wanted=false`; cancel a pending frame. During a frame: the `finally` then schedules nothing |
| show (`start`) | no pending frame and not running | `_wanted=true`; schedule one. During a frame: only `_wanted=true`; the `finally` schedules |

Invariants: (I-1) an exception in any stage cannot prevent the next frame while visible; (I-2) healthy frame cadence,
the order of optional stages and their outputs are unchanged (§3); (I-3) never two pending frames, and none while
hidden — including hide/show during a faulting frame. The guard no longer reads a consumed id as pending (this also
removes a latent double schedule on `5542ef4e`: hide+show inside a healthy frame left two pending frames). The loop
remains the single instance-owned rAF loop; there is no `window.onerror`, watchdog or second loop.

### 1.2 ISM-PRAY-005 — prayer publication ordering (D.2; R0007 contract preserved)

- **P-1 prayer stage first.** `render()`: sim-invalid → `prayer` (withdrawal + calendar) then `weather-header`.
  Otherwise `setLocLabel()` (neutral, unchanged), then the prayer stage — `model()`, `prefetchPrayerDay()`,
  `.cn/.nt/.left`, progress bar, `drawArc`, `fitCn`, rows, `renderCalendarDates(selectCalendarDisplay(M))`,
  `data-stale`; or, with no model, `withdrawPrayerPresentation()` + `renderCalendarDates(selectCalendarDisplay(null))`
  — then `weather-sync` (`syncWeather`, moved from before `model()`), then either the no-timetable optional stages
  (`weather-decision`, `weather-header`, `weather-withdrawal`, `celestial`) or `moon-geometry`, `stars`, the theme and
  `lightning`, in their previous relative order. Re-verified while reordering: nothing in the prayer stage reads
  optional-stage state (`model` does not read `weather`; `drawArc` and `selectCalendarDisplay` use `M`/`moonNow()`,
  not `moonSky`; the stale marker is set before the theme as before).
- **P-2 prayer-stage failure is truthful.** A throw in the prayer stage records `prayer`, sets `_lastRender=null`,
  publishes the existing withdrawal ("Prayer times unavailable", rows "—", calendar) and runs only the no-timetable
  optional stages; `applyTheme` never runs with a partial or undefined `M`. When the failing statement was the
  no-timetable withdrawal itself, it is not retried in that frame.
- **P-3 receipt truth.** `_lastRender` is written in a `finally` after the theme, so it always describes the prayer
  frame published by this render; `fx` is taken from this frame's completed theme stage and is `null` when the theme
  failed this frame. An earlier receipt cannot survive a newer published prayer frame.
- **Theme error behaviour retained.** `applyTheme` still rethrows after recording (accepted R0021 behaviour, asserted
  by `tests/r0021-reveal.cjs` "failed first paint keeps entry pending…"). The rethrow leaves `render()` only after the
  receipt and the lightning stage ran; every caller (loop, boot, apply, reset, loader, `SalahClock.set`) contains it.

### 3a. Same-frame clock reads under `timeScale` (quantified; not changed)

Which reads moved: inside one `render()`, `model()` captures `nowEpoch` once (unchanged; r0007-countdown asserts one
read). Three optional stages read `simNow()` themselves and now run after the prayer DOM work instead of before it:
`syncWeather` (`wxAt(simNow())`, effective only while `ADVANCING` or a control preview), `renderMoon`
(`simDate()` → `nativeLunarSnapshot`, minute cadence) and `projectStars(simDate())` (every frame only while
`ADVANCING`). `applyTheme`/`atmosphere` and `lightning` keep their position (already after the prayer stage).
The fixed-clock VM differential cannot see this; frozen scenes (`TIMESCALE` 0) read the same instant everywhere, and
at 1x the shift is sub-frame against minute/second cadence.

Measured (Chromium 148, `timeScale=1800`, `simTime=12:00`, entry time of each stage minus `model()` entry, ~50 frames,
1 ms `performance.now` granularity; `node tools/qa/r002c_clock_skew.cjs <playwright> <tree> 1800`):

| Stage | 5542ef4e / main | R002C |
|---|---|---|
| `syncWeather` | runs before `model()` (≈ 0 ms) | +1 ms median, +2 p95, +3 max |
| `renderMoon` | +0 median, +1 max | +1 median, +2 p95, +3 max |
| `projectStars` | +1 median, +1 max | +2 median, +4 p95, +8 max |
| `applyTheme` (unchanged position) | +2 median, +3 max | +2 median, +4 p95, +8 max |

At 1800× one wall millisecond is 1.8 s of simulated time, so the worst observed extra skew is ≈ 14 s simulated
(≈ 3 ms median → 2–5 s). The baseline already spread these reads over 0–3 ms within one frame.

Constraints: no accepted test requires cross-stage clock coherence within a frame. The clock tests pin `model()` to
one read (r0007-countdown) and the loop to one wall read on resume (r0020-clock), both unchanged; there is no
R0008/R0020 state-contract file. The registry entry ISM-PRAY-001 does state the invariant "one epoch feeds prayer,
calendar, sky and Moon". Read as one clock source (`simNow()`), it holds before and after R002C. Read as one instant
per frame, it was already not met on main under `timeScale` (0–3 ms spread, table above) and R002C widens that spread
to at most 8 ms in the measurement; frozen and 1x scenes meet it either way. This is reported as a residual against
ISM-PRAY-001 for its owner, not resolved here.

Per-frame sample: **not implemented.** Any shared frame sample (for example memoising `simNow()` for the duration of
`render()`) makes the optional stages read `model()`'s instant, which differs from what main produces under
`timeScale` (main's stages read 0–3 ms later than `model()`), so it cannot be byte-neutral against main there; it is
neutral only for frozen and 1x scenes, where it buys nothing. It would also change a global clock owner's semantics
outside this work order's scope. Recommended as a separate, explicitly visual-affecting proposal if wanted.

## 9. Finding for R0028 (issue 89): date harnesses, statement order and the repaired double

Facts, in order:

- On 5542ef4e (before R0028) `tests/r0001-date-sinks.cjs`, `tests/r0009-date-selection.cjs` and
  `tests/r0019-date-disclosure.cjs` each failed one case (PRA-F-06) because their element double lacked
  `style.getPropertyValue`, so the no-model `withdrawWeatherEffects` → `paintLunarOptic` threw before the calendar write.
- On the R002C branch before merging R0028, the same three passed (13/13, 22/22, 16/16) **by statement order only**:
  R002C writes the no-model calendar before the optional stages, while the defective double still threw (contained,
  recorded as `weather-withdrawal`, printed once by the harness console).
- R0028 (main bcd02af2) repaired both doubles (`tests/r0009-calendar-harness.cjs`, `tests/r0001-date-sinks.cjs`); the
  harnesses pass on main without R002C. On this merged branch they pass with **no** contained stage fault: zero
  `render stage … failed` lines in all three harness runs. So they pass for the double's reason, and R002C's order is
  not what makes them green any more.

What R0028's discrimination must keep (not changed here): the repaired harnesses should continue to detect a double
that throws in the optional stage even though R002C now contains that throw — asserting an empty
`qaState().renderFaults` (or the absence of the stage-fault console line) in the no-model cases would do it. The
product order itself is guarded by R002C's own rows (R2C-01 "no-model header after withdrawal and calendar", mutant m7c).
