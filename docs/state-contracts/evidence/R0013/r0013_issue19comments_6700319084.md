## 3. Explicit knowledge and eligibility states

One small discovery record contains target/profile identity, evidence class, supported status, bounded reason and retained matches. Conceptual statuses:

| Status | Meaning |
|---|---|
| known-new | Supported parsed evidence identifies TablissNG without legacy |
| known-legacy | Supported parsed evidence identifies legacy Tabliss; existing refusal applies |
| known-both | Both identified; new presence does not authorise legacy overwrite |
| known-neither | Supported complete relevant metadata parsed and neither identified under the declared detector |
| unknown | Absent, unreadable, malformed, unsupported or insufficient metadata/parser evidence |

Missing metadata is not automatically a proven empty inventory. If a supported new-profile route establishes a narrower safe absence condition, name and test that separate evidence; otherwise use unknown/reason metadata-absent. A grep hit can support a conservative legacy warning, but grep no-match cannot certify known-neither without complete supported interpretation.

Target eligibility is separate: eligible-known, legacy-refused, unknown-held, or not-applicable/no-profile under declared policy. Knowledge of an eligible target is not knowledge that an extension is installed or an artifact is ready.

Bash's current `hasNew|hasOld|matches` tuple cannot encode unknown. Introduce an explicit status/reason or a tagged/versioned local result and migrate every real parser/caller coherently. Preserve Bash3.2 language restrictions, set-e/nounset behavior, structured stdout and diagnostics on stderr. Do not silently shift tuple positions or add unsupported associative arrays/builtins.

PowerShell may retain old properties alongside explicit Status/Reason, but current callers must require the status; false flags alone cannot imply absence. Catching an exception must not return a success-shaped known result. Keep source encoding and Windows PowerShell5.1/supported7 compatibility.
